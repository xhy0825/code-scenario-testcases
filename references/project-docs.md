# 项目了解文档模板参考（阶段0A 产出）

> 生成用例前对项目做全面了解，产出 6 份独立 Markdown 文档到 `testcase/<项目名>/doc/`。
> 每份文档统一头部 + 对应章节；信息源按"需求注入优先 + 代码推断 + 标注待确认"。

## 统一文档头部（每份文档必填）

```markdown
# <文档标题>

- 版本：v<N>
- 生成时间：YYYY-MM-DD HH:MM
- 信息来源：需求注入 / 代码推断 / 待确认
- 项目：<项目名>
```

> 注意：上述代码块内为字面示例，实际写文件时保留外层 markdown 结构。

## 版本命名与递增规则

- 文件名：`<主题>_v<N>.md`（如 `需求分析_v1.0.md`、`架构设计_v1.1.md`）
- 输出目录：`testcase/<项目名>/doc/`（不存在则创建）
- 递增判定：扫描该目录已有 `<主题>_v*.md` 取最高版本
  - 本次信息有**实质变化** → 版本 +1，旧版本保留
  - 无实质变化 → 复用当前版本，仅刷新文档头"生成时间"
  - `-diff` 模式必有变更 → 递增；`-all` 模式对比 `git log` 最近提交 → 有变递增、无变复用
- 语义化：需求/架构重大变化手动升次版本（v1.0→v2.0），常规迭代升修订号（v1.0→v1.1）

## 文档一：项目背景

```markdown
## 1. 项目定位
- 一句话说明项目是什么、解决什么问题

## 2. 服务对象
- 使用者/受益方

## 3. 技术栈
- 语言 / 框架 / 存储 / 中间件 / 构建

## 4. 模块概览
- 模块名：职责（来源：代码推断 / 用户说明）
```

## 文档二：需求分析

```markdown
## 1. 功能需求
- 功能名：描述（来源：需求注入 / 代码推断，标注待确认）

## 2. 业务规则
- 必填 / 金额 / 权限 / 防重 / 时效 / 状态机 / 安全 逐条列出（来源标注）

## 3. 非功能需求
- 性能 / 安全 / 可用性 / 兼容性（有则写，无则标注"未提供"）

## 4. 待确认项
- 无需求文档时全部标注"推断（待与需求确认）"
```

## 文档三：架构设计

```markdown
## 1. 分层与模块
- 表现层 / 业务层 / 数据层（或项目实际分层）

## 2. 模块依赖关系
- A → B（方向 + 说明）

## 3. 入口与出口
- 功能入口方法 / 外部依赖调用点（接口、DB、缓存、第三方）

## 4. 数据流
- 关键链路的数据流转（来源：代码推断）

## 5. 关键设计
- 设计模式 / 特殊机制（来源：代码推断）
```

## 文档四：业务流程

```markdown
## 1. 主流程
- 步骤 1 → 步骤 2 → ……（来源标注）

## 2. 分支流程
- 条件：分支行为

## 3. 异常流程
- 异常触发：处理与返回

## 4. 流程要点
- 事务 / 幂等 / 状态迁移等关键点（来源标注）
```

## 文档五：功能清单

```markdown
## 场景 → 功能 → 入口

| 业务场景 | 功能 | 入口方法 | 说明 |
|---|---|---|---|
| 订单管理 | 创建订单 | createOrder() | （来源：代码推断） |

- 与第 5 步"功能级覆盖"、追溯矩阵对照使用
```

## 文档六：使用场景

```markdown
## 1. 用户角色
- 角色：职责

## 2. 典型场景
- 场景：谁在何时用什么功能达到什么目的

## 3. 场景与功能映射
- 使用场景 → 涉及功能（来源：需求注入 / 代码推断）
```

## 撰写要点

- 每条信息尽量标注来源（需求注入 / 代码推断 / 待确认），不假装确定
- 无需求文档时，需求分析整体标注"推断（待与需求确认）"
- 外部依赖/框架隐含行为标注"依赖外部实现"，与用例"推断（需联调）"口径一致
- 文档为**项目了解产物**，与验证设计的"基线/验证点清单"是不同视角，不互相替代
