# 验证点（Verification Point）参考

**本文件是"验证点"概念的唯一权威**——定义、分类、识别方法、与判定点的关系。SKILL.md 第 2/3 步据此把"业务场景 → 功能"映射到可验证的行为点，再逐点设计用例。

## 1. 定义

**验证点（Verification Point）= 一个功能"值得验证的一个行为点"。**

- 每条用例 = 一个验证点的可执行化（前置 + 步骤 + 预期 + 验证方法 + 可自动化程度）
- 一个功能通常有多个验证点；验证点清单是该功能的"验证什么"清单，也是覆盖核对（需求验证点 X/Y）的追溯依据
- 验证点强调"验证这个行为"（可观察、可判定），而非"这条 if 存在"——后者只是前者的代码来源

## 2. 验证点分类（6 类）

| 类别 | 含义 | 典型识别特征 | 对应代码来源 |
|---|---|---|---|
| ① 判定点分支 | 条件真/假各产生不同行为的路径 | `if/else`、`switch/case`、三目、guard | `code-snippet-templates.md` 场景 1-3/5-9/13 |
| ② 输入约束 | 参数必须满足的框架约束/类型 | `@NotNull/@Min/@Max/@Pattern/@Size` 等 | `input-constraints.md` |
| ③ 外部契约 | 对依赖（DB/缓存/第三方/内部 service）返回的契约状态的处理 | `xxxService.xxx()`、`xxxDao.xxx()` 调用后的分支 | `external-contracts.md`（契约五态） |
| ④ 状态迁移 | 状态字段读取/改写的合法迁移路径 | 状态字段 + `if (x.getStatus() == ...)` 改写 | `code-snippet-templates.md` 场景 10 |
| ⑤ 异常路径 | 异常/空值的处理行为 | `try/catch`、判空后的 NPE 风险点、吞异常 | `code-snippet-templates.md` 场景 11-12 |
| ⑥ 业务规则 | 需求定义的业务规则（必填/金额/权限/防重/时效/越权） | 无代码判定点时 → 规则缺口；有 → 已覆盖 | `rule-gap-checklist.md` |

> ⑥ 是"需求验证点"；①②③④⑤ 是"代码可测点"。验证设计 = ⑥ ∪ ①②③④⑤。

## 3. 识别方法

对每个功能，按两步建验证点清单：

1. **代码可测点**（第 3 步各识别规则产出）：扫判定点 → 每个分支一个可测点；扫约束注解 → 每个约束；扫外部调用 → 每个契约点；扫状态字段 → 每个状态取值；扫 try/catch/判空 → 每个异常/空值路径
2. **需求验证点**（第 5 步规则缺口审查 + 需求/契约注入产出）：逐条对照业务规则清单，规则有代码判定点 → 成为已覆盖的验证点；无 → 写入 `coverage.rule_gaps`（待补验证点 / 疑似缺陷）

## 4. 与判定点的关系（机器基准）

```
验证点 = 判定点 ∪ 输入约束 ∪ 外部契约 ∪ 状态迁移 ∪ 异常路径 ∪ 业务规则
判定点 ⊆ 代码可测点 ⊂ 验证点
```

- **判定点**是 `enumerate_decision_points.py` 枚举的 if/catch/switch 行，作**判定点覆盖分母**（机器基准，漏测亮红灯）
- **验证点**更宽：包含判定点之外的需求规则与约束/契约。所以"判定点 100% 覆盖"≠"验证设计完整"——`需求验证点覆盖 X/Y` 与 `规则缺口` 单独列，避免"100% 却缺关键规则"的错觉

## 5. 用例↔验证点映射示例（引用真实案例）

| 用例 | 功能 | 验证点 | 分类 | 说明 |
|---|---|---|---|---|
| TC-EXAM-005 | 考试交卷 | 空答案集合不应被当作已答完提交 | ① 判定点分支 | 循环不执行时 `hasFinish` 恒 true 的缺陷路径 |
| TC-MINE-008 | 新增缴费记录 | 非 00004 失败码应判为失败而非"上传成功" | ⑥ 业务规则 | 代码只判 `00004`，其余一律成功——规则缺口/缺陷 |
| TC-PROT-005 | 任务协议参数封装 | 加密异常不应被吞、应返回可用载荷 | ⑤ 异常路径 | `catch` 仅打印日志后返回空 map |
| TC-CACHE-005 | 登录缓存清空 | 退出登录后 `userType` 不应残留 | ⑥ 业务规则 | `clear()` 未重置 `USERTYPE`——残留缺陷 |
| TC-MEET-006 | 发布会议 | 签到开始时间为空应被拦截 | ② 输入约束 | 复制粘贴 bug：误判 `mStartTime` 导致校验失效 |
| TC-TASK-019 | 任务详情解密 | 解密失败应给用户反馈而非静默 | ③ 外部契约/⑤ 异常路径 | `catch` 仅 `printStackTrace`，View 无回调 |

> 同一验证点可能跨分类（如外部契约失败 + 异常吞掉）；标注主导分类即可，备注写全。

## 6. 资深审查要点

1. **验证点 ≠ 判定点**：别把"每条 if 一条用例"当全部——漏掉输入约束/外部契约/业务规则 = 验证设计不完整
2. **⑥ 业务规则是验证设计的灵魂**：代码驱动只能发现"已写的"，⑥ 的缺口（防重、金额、越权、时效）才是"该有却没有"的验证点
3. **可观察性**：每个验证点的预期必须落在验证方法可观察的对象上（界面/接口/数据/日志），否则是"伪验证点"
4. **数量收敛**：单功能验证点建议 ≤12，超出按 P0/P1 聚焦并说明（见 `execution-boundaries.md`），避免用例爆炸
