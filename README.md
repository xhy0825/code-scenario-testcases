# code-scenario-testcases

**面向验证设计的研发自测用例生成器** —— 读取业务代码（+ 可选需求/契约），自动梳理 **业务场景 → 功能 → 验证点 → 用例** 四级结构，设计研发自测用例 Excel。每条用例回答三个问题：**验证什么**（验证点）、**怎么验证**（验证方法）、**能否自动化**（可自动化程度）。

- **语言无关**：支持 Java / Go / Python / JavaScript / TypeScript / C# / C / C++ / Rust 等主流语言
- **可核算的覆盖率**：入口覆盖、判定点覆盖以真实代码盘点为分母；需求验证点覆盖对照需求逐条核算，缺漏会亮红灯而非悄悄漏
- **支持变更范围扫描**：`-all` 全量、`-diff` 当前未提交变更、`-diff [commitId]` 指定提交之后变更；另有 `-doc` 仅生成项目文档、`-doc -diff` 仅按变更更新文档版本号、`-xlsx` 只生成 Excel 跳过文档

## 一、功能介绍

### 1.1 核心能力

| 能力 | 说明 |
|---|---|
| **四级结构** | 业务场景 → 功能 → **验证点** → 用例，从用户视角到可验证行为点逐层对应（见 `references/verification-points.md`） |
| **验证点设计** | 每条用例标注验证点（验证什么：判定点分支/输入约束/外部契约/状态迁移/异常路径/业务规则）、验证方法（怎么验证：界面/接口/数据/日志/联调）、可自动化程度（能否自动化：可单测/组件/端到端/仅人工联调） |
| **场景类型标注** | 每条用例标注 **正常流程 / 异常流程**（按路径最终现象分类，看现象不看分支方向），每个功能保证至少 1 条正常流程用例，Excel 可按场景类型筛选；**「场景类型」列文字着色**（正常流程绿色 / 异常流程红色，其余列保持默认黑），目视即区分成功/拒绝路径 |
| **触发方式标注** | 每条用例**前置条件**以 `[页面触发]`/`[mock数据]` 开头明确触发方式（页面 UI 操作 vs 接口/mock/数据预置），执行者可据此确定自测环境（页面环境 or 数据构造） |
| **分支全覆盖** | 把 `if/else`、`switch/case`、三目、guard clause、循环内条件统一建模为"判定点"，每个分支一条用例 |
| **复合条件拆分** | `a && b` 拆原子条件：成功路径 1 条 + 每个子条件"不满足"各 1 条，让自测者明确判定为假的成因；高安全场景可选 MC/DC |
| **边界值用例** | 对 `>` `<` `>=` `<=` `==` 比较补充边界用例（等于边界、边界±1、null/空），标注"边界" |
| **状态机建模** | 识别状态字段（如 `order.getStatus()`）的取值与迁移，前置条件覆盖每个状态值 |
| **调用链分析** | 场景内入口→直接→间接调用路径组合；`-diff` 标记变更函数调用方"间接受影响" |
| **机器枚举覆盖率基准** | 判定点覆盖率的**分母由 `enumerate_decision_points.py` 确定性枚举**，漏了会亮红灯而非分母变小 |
| **预期结果** | 统一为 **`UI显示:`（页面/客户端现象） + `数据结果:`（接口/数据/状态变化）** 双部分，纯接口写 `无(纯接口)`、纯展示写 `无(纯展示)`；错误串**原样摘录**；每条预期结果标注来源（代码摘录 / 推断需联调） |
| **覆盖率核算** | 判定点盘点清单 + 机器枚举 + 第二遍回读双向核对，产出覆盖统计与判定点→用例追溯矩阵 |
| **变更回归覆盖** | `-diff` 模式下定位受影响函数，以**整函数**为单位生成完整分支用例（防一次改动回归到其它分支） |
| **命令式范围控制** | 用 `code-scenario-testcases -all / -diff / -diff [commitId] / -doc / -doc -diff / -xlsx` 指令精确控制扫描范围；`-doc` 只生成当前项目文档（阶段0A 6 份 doc）、`-doc -diff` 只按变更更新文档版本号、`-xlsx` 跳过文档只生成 Excel |
| **测试结果跟踪** | 用例表内置 **测试结果列（PASS/FAIL 下拉）**，研发自测执行时直接勾选 |
| **Excel 美化与阅读体验** | 行高按内容自适应（换行内容完全显示）、数据行斑马纹、统一微软雅黑字体、场景类型列着色（正常绿/异常红）；覆盖说明分节标题浅蓝、子表蓝底白字表头 |
| **语言无关建模** | 条件逻辑统一建模，语言差异只影响入口识别与语法写法（详见 `references/language-guide.md`） |
| **专业角色** | 以**资深研发自测架构师**身份执行：测试设计专家 / 覆盖率工程师 / 代码质量审查者三重视角，自检准则为"每条用例可执行、高风险优先、诚实交付、报告专业" |
| **需求/契约注入** | 调用时可附带需求描述/接口契约/验收标准，预期结果优先对照需求规则、代码仅作补充，发现"需求有规则、代码无实现"时标记疑似缺陷 |
| **规则缺口审查** | 对照业务规则清单（`references/rule-gap-checklist.md`）反向审查，找出"该有却没有"的分支（金额/库存/权限/防重/并发/状态迁移等），单独列示、不虚增覆盖率 |
| **输入约束分析** | 从参数约束注解（`@NotNull/@Min/@Max/@Pattern` 等）与类型生成等价类用例（合法/非法/边界/空），独立于分支覆盖测"代码隐含的输入约束" |
| **外部契约建模** | 对依赖调用点（`xxxService/xxxDao/xxxClient`）建模**契约五态**（成功有效/成功空值/抛异常/超时/降级），mock 各状态生成分支用例，把"推断（需联调）"升级为确定性建模 |
| **高级维度分析** | 数据流/null 传播、时间/时序/幂等、权限矩阵、容量/计算边界（默认启用）；MC/DC 与业务链路（高安全/全链路按需启用），见 `references/advanced-dimensions.md` |

### 1.2 产出物

一次调用产出两个文件，统一输出到 **skill 安装目录的 `testcase/` 文件夹**：

- **多项目**：按项目名建子文件夹 `testcase/<项目名称>/`
- **Excel 命名**：`<项目名称>_<日期>_<版本>.xlsx`（如 `订单管理系统_20260801_v1.0.xlsx`，版本默认 v1.0 可指定）

```
testcase/
├── 订单管理系统/
│   ├── 订单管理系统_20260801_v1.0.xlsx
│   └── doc/
└── 用户中心/
    ├── 用户中心_20260801_v1.0.xlsx
    └── doc/
```

每个项目目录下：

| 目录/文件 | 说明 |
|---|---|
| 研发自测用例 Excel（`.xlsx`） | 主 sheet + 「覆盖说明」sheet |
| 结构化用例 JSON（`cases.json`） | 供二次消费/接入测试平台，与 Excel 同目录 |
| `doc/` | 前置项目文档（第 0.5 步产出）：6 份版本化 Markdown（项目背景/需求分析/架构设计/业务流程/功能清单/使用场景）；`-doc` 指令可只产出文档不生成用例，`-doc -diff` 只按变更更新版本号，`-xlsx` 跳过本目录不产出 |

#### 主 sheet 列说明

| 列 | 说明 |
|---|---|
| 用例编号 | `TC-<场景缩写>-<序号>` |
| 业务场景 | 用户视角动作（如"订单管理"） |
| 功能 | 一个可独立触发的业务入口 |
| 用例名称 | "功能名 + 分支语义" |
| 场景类型 | 正常流程（成功完成功能）/ 异常流程（被拒绝/失败），按路径最终现象分类；每个功能至少 1 条正常流程；**本列文字着色：正常流程绿色、异常流程红色（其余列默认黑）** |
| 验证点 | 该用例验证的行为点（判定点分支/输入约束/外部契约/状态迁移/异常路径/业务规则） |
| 前置条件 | 以 `[页面触发]`/`[mock数据]` 开头标注触发方式 + 数据/状态前提（页面操作→页面触发；接口/mock/数据预置→mock数据；不得写成操作步骤） |
| 操作步骤 | 可复现步骤（调用入口 + 关键参数 + 数据准备） |
| 验证方法 | 怎么验证：界面操作 / 接口响应 / 数据状态 / 日志 / 需联调 |
| 可自动化程度 | 能否自动化：可单测 / 可组件测试 / 可端到端 / 仅人工+联调 / 需联调确认 |
| 优先级 | P0 核心/安全校验；P1 主要分支；P2 边缘/兜底 |
| 预期结果 | **核心字段**，统一为 `UI显示:`（页面/客户端现象）+ `数据结果:`（接口/数据/状态变化）双部分，纯接口/纯展示显式标注，必须可判定且单一 |
| 测试结果 | 留空，下拉选择 PASS / FAIL（数据验证） |
| 备注 | 外部依赖、待验证事项、边界提示 |
| 代码位置 | 分支所在 `文件:行号` + 方法名 |

#### 「覆盖说明」sheet

- **覆盖统计**：业务入口覆盖 X/Y、判定点覆盖 X/Y（机器基准）、需求验证点覆盖 X/Y（对照需求逐条）
- **可自动化程度分布**：可单测/可组件/可端到端/仅人工联调 的用例数量分布（验证计划编排依据）
- **场景类型分布**：按功能统计 正常流程/异常流程 用例数（每个场景正常+异常覆盖可核算）
- **变更范围**（`-diff` 模式）：变更文件数、受影响函数、新增判定点
- **缺口列表**：未达 100% 时列出具体缺口
- **判定点 → 用例追溯矩阵**：每个判定点的每个分支映射到用例编号
- **标注区**：缺口 / 验证缺口 / 无法静态验证项 / 规则缺口

### 1.3 四级结构

```
业务场景（用户视角：如"订单管理"）
└── 功能（业务入口：查询订单 / 创建订单 / 取消订单）
    └── 验证点（值得验证的行为点：判定点分支/输入约束/外部契约/状态迁移/异常路径/业务规则）
        └── 用例（该验证点的可执行化：前置 + 步骤 + 验证方法 + 可自动化程度 + 预期）
```

### 1.4 需求/功能/用例 ↔ 代码 场景/条件/现象 的对应关系

本 skill 的产出逻辑，本质是两条链的逐层映射：

**业务侧（从需求出发）：** `需求（要什么）→ 功能（做到什么）→ 测试用例（验证什么）`

**代码侧（从实现出发）：** `场景（哪条路径）→ 条件（在哪分叉）→ 现象（执行后看到什么）`

| 业务侧 | 代码侧 | 对应方式 |
|---|---|---|
| 需求 | 功能边界 | 需求规定"做什么"，落到代码是一组功能入口的集合 |
| 功能 | 业务入口方法 | 一个功能 = 一个可触发入口（接口/方法），如"创建订单"=`createOrder()` |
| 测试用例 | 条件分支（路径场景） | 用例的**前置条件** = 把某条件拨到目标取值；**操作步骤** = 走通该路径的方式；用例本身 = 一条执行路径 |
| 预期结果 | 现象 | 该路径执行后的**可观察输出**（错误串原样摘录、返回值、状态变化、页面展示） |

**一句话**：功能在代码里是一个入口，测试用例是一条"条件定死后的执行路径"，预期结果是这条路径走完后的现象。

**示例（订单创建）：**

```java
if (userId == null)    → 抛 BizException("用户不能为空")      // 条件A
if (amount <= 0)       → 抛 BizException("订单金额必须大于0")  // 条件B
if (!checkStock(...))  → 抛 BizException("库存不足")          // 条件C
switch (payType)       → wechat / alipay / 支付方式不支持       // 条件D
```

| 功能 | 测试用例 | 前置条件（条件取值） | 预期结果（现象） |
|---|---|---|---|
| 创建订单 | TC-001 用户为空校验 | 条件A=真（userId=null） | 抛"用户不能为空"，不生成订单 |
| 创建订单 | TC-002 金额非法校验 | 条件B=真（amount=0） | 抛"订单金额必须大于0" |
| 创建订单 | TC-003 库存不足校验 | 条件C=真（库存返回false） | 抛"库存不足" |
| 创建订单 | TC-004 微信支付 | 条件D=case1 | 订单.payChannel=wechat，返回订单 |
| 创建订单 | TC-005 支付方式不支持 | 条件D=default | 抛"支付方式不支持" |

**本 skill 是反向推导**：读代码 → 识别功能入口（对应"功能"）→ 聚合业务场景（对应"需求归属"）→ 识别条件判定点（对应"路径场景"）→ 每条分支生成用例（前置=条件取值、步骤=触发路径、预期=现象）。

**对应不上的三种情况（诚实处理）：**

| 情况 | 后果 | 处理 |
|---|---|---|
| 需求存在但代码未实现 | 无对应入口/分支 | 无法覆盖 → 显式标注"需求未实现场景" |
| 分支调用外部依赖（DB/第三方） | 分支存在但"现象"取决于外部 | 预期结果按代码现状写，标注"推断（需联调）" |
| 框架隐含行为（反序列化、鉴权） | 不在业务函数体里 | 列入"无法静态验证项" |

> 对应闭环只覆盖"已落到代码里的需求"；需求没进代码的部分，skill 会诚实标"覆盖不了"，而非硬凑。

## 二、架构设计

### 2.1 目录结构

```
code-scenario-testcases/
├── SKILL.md                        # 技能主体：工作流程 + 字段规则 + 调用方式
├── install.sh                      # 一键部署到 Claude Code 运行时目录（git commit 后自动触发）
├── references/
│   ├── language-guide.md           # 语言适配参考（按需加载）
│   │   ├── 文件扩展名 → 语言映射
│   │   ├── 各语言"功能入口"识别启发式
│   │   ├── 条件分支语法对照表
│   │   ├── 判定点统一建模规则
│   │   └── 隐含条件识别清单（lambda/try-catch/可选链/类型判断等）
│   ├── code-snippet-templates.md   # 代码片段→用例模板参考（13 类条件结构场景 + 资深审查要点）
│   ├── rule-gap-checklist.md       # 业务规则缺口审查清单（反向审查，发现"该有却没有"的分支）
│   ├── input-constraints.md        # 输入约束分析参考（参数约束注解对照 + 等价类生成）
│   ├── external-contracts.md       # 外部契约建模参考（依赖调用五态：成功/空值/异常/超时/降级）
│   ├── advanced-dimensions.md      # 高级分析维度（数据流/null 传播、时间/时序/幂等、权限矩阵、容量/计算、MC/DC、业务链路）
│   ├── verification-points.md      # 验证点清单参考（验证点概念与识别：代码可测点 ∪ 需求验证点）
│   ├── execution-boundaries.md     # 执行边界清单（排除生成代码/样板类，限制调用链/嵌套/原子数/用例数上限）
│   ├── help.md                     # 使用帮助（`-help` 指令输出）
│   └── project-docs.md             # 前置项目文档模板（阶段0A 产出 6 份版本化文档，`-doc` / `-doc -diff` 指令）
├── scripts/
│   ├── generate_excel.py            # 结构化 JSON → Excel 生成脚本
│   │   ├── 主 sheet（15 列 + 行高自适应/斑马纹/场景类型列着色 + 筛选 + 冻结首行）
│   │   ├── 测试结果列 PASS/FAIL 下拉（数据验证）
│   │   └── 「覆盖说明」sheet（覆盖统计/可自动化分布/场景类型分布/功能覆盖清单/变更范围/追溯矩阵/功能↔用例/标注区）
│   └── enumerate_decision_points.py # 确定性判定点枚举（覆盖率分母基准，多语言）
└── evals/
    └── evals.json                  # 测试用例定义（5 个 eval，用于回归验证）
```

### 2.2 数据流

```
扫描目录 / git diff
   │
   ▼
① 扫描过滤源码 ──▶ ② 识别业务场景/功能（产出入口清单）
   │
   ▼
③ 逐功能提取判定点，生成分支用例（复合条件拆分 / 边界值 / 状态机 / 调用链）
   │
   ▼
④ 覆盖率核对（enumerate_decision_points.py 机器枚举作分母 + 双向回读 + 覆盖统计）
   │
   ▼
⑤ 整理成 cases.json（cases + coverage 对象）
   │
   ▼
⑥ scripts/generate_excel.py ──▶ 研发自测用例.xlsx + cases.json
```

### 2.3 cases.json 数据结构

```jsonc

    "change_scope": {              // -diff 模式才产生
      "mode": "diff",
      "changed_files": ["OrderService.java"],
      "affected_functions": ["createOrder"],
      "new_decision_points": ["if (amount > 10000)"]
    },
    "uncovered": [],               // 缺口，为空表示全覆盖
    "verification_gaps": ["订单幂等校验无用例"],        // 需求验证点缺用例

    "rule_gaps": [{"category": "防重", "function": "创建订单", "gap": "未校验重复提交", "confirm_with": "需求"}]
  }
}
```

### 2.4 关键设计决策

| 决策 | 理由 |
|---|---|
| **判定点统一建模** | `if/else/switch/三目/guard/循环内条件` 都抽象为"判定点 → 真/假分支"，跨语言一致 |
| **复合条件拆原子条件** | `a && b` 的成功路径 1 条 + 每个子条件"不满足"各 1 条，明确判定为假的成因，避免只测一种情况 |
| **边界值用例** | `> < >= <= ==` 补 边界/边界±1/null/空（P2 标注"边界"），抓边界缺陷 |
| **嵌套条件不笛卡尔积** | 内层分支把外层取值写进**前置条件**，每个判定点自身覆盖真假分支，避免用例爆炸 |
| **状态机建模** | 状态字段取值与迁移显式建模，读取状态的判定点覆盖每个状态值，避免只测到某一状态 |
| **调用链分析** | 跨函数参数/状态路径组合；`-diff` 用 grep 找调用方标记"间接受影响" |
| **受影响函数整函数覆盖**（-diff） | 一次改动可能回归到该函数其它分支，整函数覆盖比"只改哪测哪"安全 |
| **机器枚举分母** | 覆盖率分母 = `enumerate_decision_points.py` 枚举的真实判定点，而非模型记忆；漏了亮红灯 |
| **覆盖率以"代码可表达范围"为分母** | 外部依赖行为、需求未实现场景无法由静态代码保证 → 显式标注而非假装覆盖 |
| **第二遍回读双向核对** | 有判定点无用例 → 补；有用例无代码依据 → 删/标；让"漏没漏"可核算、可追责 |
| **场景类型显式标注** | 成功路径与拒绝/失败路径用「场景类型」列显式区分，Excel 可直接筛选"正常流程"，确保每个功能正常主路径不被漏测 |
| **前置触发方式 + 预期双结果标注** | 前置条件用 `[页面触发]`/`[mock数据]` 明确触发方式（页面环境 vs 数据构造），预期结果强制分离 `UI显示:`（界面现象）与 `数据结果:`（落库/接口状态），研发自测可区分"界面对了数据错"与"数据对了界面没展示"两类缺陷 |

### 2.5 工作流程（8 步，三阶段，对齐研发自测经验流程）

**阶段0 前置界定**
0. **需求理解与范围界定**：成功判据三问（给谁用 / 输入输出契约 / 成功判据）+ 改动范围与测试边界界定（外部依赖 mock 不真测），产出自测范围说明并入双基线

**阶段0A 项目了解**
0.5. **项目了解与文档产出**：全面了解项目背景/需求/架构/业务流程/功能/使用场景，产出 6 份版本化文档到 `testcase/<项目名>/doc/`（文件名带版本号，有实质变化才 +1、旧版保留）；功能清单/业务规则供后续覆盖与缺口审查复用；`-doc` / `-doc -diff` 指令只执行本步即结束，`-xlsx` 指令跳过本步

**阶段1 验证设计**
1. **扫描过滤与建立双基线**：递归收集源码，跳过构建产物/依赖/测试文件；建**入口清单（代码基线）** + **业务规则清单（需求基线，无需求时从业务常识/代码可推断规则建立，标注"待与需求确认"）**
2. **识别场景、功能与验证点**：按 Controller/业务实体/模块聚合场景；每功能建「验证点清单」（代码可测点 ∪ 需求验证点，后者对照第 0/1 步基线）
3. **设计验证用例**：逐验证点可执行化，套 13 类展开模板（复合拆原子/嵌套不笛卡尔积/边界补值），产出 15 列用例 + 字段质量自检
4. **高级维度补齐**：数据流/null 传播、时序/幂等、权限矩阵、容量/边界（A-D 默认）；MC/DC、业务链路（E/F 按需）
5. **覆盖率核对**：判定点机器枚举作分母 + 需求验证点 X/Y + 高级维度检查点 + 逐功能 100% 承诺
6. **规则缺口审查**：对照第 1 步业务规则基线逐条反向核对，无对应分支 → 写入 `coverage.rule_gaps`（疑似缺陷）

**阶段2 执行收尾**
7. **生成 Excel 与汇报**：过发布门禁（字段质量自检）→ `cases.json` → `generate_excel.py` → xlsx（含覆盖说明 sheet）；汇报统计 + 功能级覆盖 + 验证计划 + **自测结论**（是否可提测）+ 需求偏差项
8. **自测执行与收尾（可选）**：冒烟先行（先跑 P0）→ FAIL 闭环（定位 → 修复 → 重跑该条 → 重跑相邻）→ 需求偏差确认 → 回补用例 → 收尾交付（汇总 + 遗留清单 + 自测结论）

## 三、使用帮助

### 3.1 环境要求

- Claude Code（本 skill 运行环境）
- Python 3 + `openpyxl`（生成 Excel 用，缺失时先执行 `pip install openpyxl`）
- `-diff` 模式需要 git 仓库

### 3.2 调用方式

| 指令 | 含义 | 扫描范围 |
|---|---|---|
| `code-scenario-testcases -all` | 全量扫描 | 整个目录的业务代码（默认行为） |
| `code-scenario-testcases -diff` | 当前变更 | 仅未提交变更（工作区+暂存区+未跟踪新文件）涉及的代码 |
| `code-scenario-testcases -diff [commitId]` | 指定提交之后 | 从 `[commitId]` 到当前（含未提交）的变更代码 |
| `code-scenario-testcases -doc` | 仅生成项目文档 | 只执行阶段0A（第0.5步），产出 6 份版本化 doc，不生成用例 Excel |
| `code-scenario-testcases -doc -diff` | 仅按变更更新文档版本号 | 按 `git diff` 判断信息实质变化：有变化的主题文档版本 +1、无变化复用当前版本；不生成用例 Excel |
| `code-scenario-testcases -xlsx` | 只生成 Excel 跳过文档 | 跳过阶段0A（第0.5步），直接扫描生成用例 Excel，不产出 doc 文档 |
| `code-scenario-testcases -help` | 使用帮助 | 输出基本使用说明并结束（不扫描） |

也支持自然语言触发，例如：

- "根据 D:/project/order 目录下的代码生成研发自测用例"
- "把 createOrder 接口的 if/else/switch 分支整理成测试用例"
- "我刚改了注册逻辑还没提交，用 -diff 生成本次变更的自测用例"

### 3.3 输入方式

- **目录**（推荐）：递归扫描其中源码文件
- **单个文件 / 单个函数**：只分析指定对象
- **粘贴的代码片段**：直接贴进对话
- **需求/契约（可选）**：附上需求描述、接口契约或验收标准，让预期结果对照需求规则、并触发"规则缺口审查"

未指定范围时默认全目录扫描，并在汇报中说明覆盖范围。

> **代码片段 → 用例模板参考**：生成用例时，skill 会对照 `references/code-snippet-templates.md` 的 **13 类条件结构模板**（简单 if、if-else、多路链、嵌套、switch、复合条件、三目、循环内条件、边界比较、状态机、try/catch、判空、多 case 合并/类型判断）定位片段类型并套用展开，每个模板都给出"代码片段 + 判定点分析 + 用例表格"；核心高风险场景还带**资深审查要点**（该结构的高风险点/易错点/优先级建议）。多结构叠加时再按第 3 步规则（嵌套不笛卡尔积、复合拆原子、边界补值）合并。

### 3.4 使用示例

**示例 1：全量扫描**

```
code-scenario-testcases -all
```

扫描当前项目全部业务代码 → 输出到 skill 安装目录的 `testcase/<项目名>/<项目名>_<日期>_<版本>.xlsx`（+ 同目录 `cases.json`）。多项目各自独立文件夹。

**示例 2：当前未提交变更**

```
code-scenario-testcases -diff
```

用 `git diff HEAD` 定位变更文件 → 定位受影响函数 → 对受影响函数生成完整分支用例，备注标注"本次变更影响"，覆盖说明单列变更范围。

**示例 3：指定提交之后的变更**

```
code-scenario-testcases -diff a1b2c3d
```

`git diff a1b2c3d` 得到该提交之后到当前的全部变更（含已提交 + 未提交），适合"上一个发布节点之后我改了什么，就测什么"。

**示例 4：仅生成当前项目文档**

```
code-scenario-testcases -doc
```

只执行阶段0A（第 0.5 步 项目了解与文档产出），产出 `testcase/<项目名>/doc/` 下 6 份版本化 Markdown（项目背景/需求分析/架构设计/业务流程/功能清单/使用场景），不生成测试用例 Excel。适合"先沉淀项目文档、后续再出用例"的场景。

**示例 5：仅按变更更新文档版本号**

```
code-scenario-testcases -doc -diff
```

在已有 `doc/` 文档基础上，用 `git diff` 判断本次变更对哪些文档主题有实质影响 → 这些文档版本 +1（旧版保留）、其余无变化主题复用当前版本。只更新文档，不生成用例 Excel。

**示例 6：只生成 Excel，跳过文档**

```
code-scenario-testcases -xlsx
```

跳过阶段0A（第 0.5 步文档产出），直接从第 1 步扫描生成用例 Excel；适合项目文档已沉淀、本次只想快速出用例表。覆盖说明中标注"跳过阶段0A"。

### 3.5 输出解读

打开生成的 Excel：

1. **主 sheet**：按行一条用例。建议按「优先级」筛选，先执行 P0（核心流程/权限安全校验）
2. **测试结果列**：执行时点开下拉选 PASS / FAIL；未执行留空
3. **覆盖说明 sheet**：
   - 看「判定点覆盖」是否为 X/X —— 不到 100% 时「缺口」会列出漏了什么
   - 追溯矩阵帮你定位"某条用例测的是代码哪一行哪个条件"
   - 「无法静态验证项」是需要你在自测环境额外验证的（如外部依赖）

### 3.6 覆盖率口径与边界

- 覆盖率以**代码可表达的范围**为分母（入口清单、判定点盘点），不包含：
  - 需求存在但代码未实现的场景
  - 外部系统行为（DB / 缓存 / 第三方接口）
  - 框架级隐含行为（参数反序列化、鉴权拦截）
- 这些项会**显式标注**在「无法静态验证项」中，而不是假装覆盖
- 代码本身写死/未实现的行为，按代码现状如实写出并在备注标注

### 3.7 常见问题

| 问题 | 处理 |
|---|---|
| 目录不是 git 仓库 | `-diff` 自动回退为全量扫描，并在汇报中说明原因；`-doc` 不依赖 git，可直接使用；`-doc -diff` 回退为 `-doc` |
| `-diff` 但没有变更 | 变更集为空时回退全量扫描，汇报说明 |
| 只想先生成项目文档 | 用 `code-scenario-testcases -doc`，只产出 6 份版本化 doc，不生成用例 Excel |
| 已有文档只想按变更更新版本号 | 用 `code-scenario-testcases -doc -diff`，只对实质变化主题的文档版本 +1 |
| 已有文档只想快速出用例 Excel | 用 `code-scenario-testcases -xlsx`，跳过文档直接生成用例表 |
| 环境缺 openpyxl | 先 `pip install openpyxl`，脚本会提示 |
| 外部依赖无法静态验证 | 预期结果按代码现状书写，在「无法静态验证项」标注，需自测环境验证 |
| 依赖库/SDK 会生成用例吗 | **不会**——只测项目自身业务代码，依赖内部实现一律排除（第 1 步跳过依赖目录）；对依赖调用的判定点仍会测，但预期结果标注"推断（需联调）" |
| 生成代码/样板类会测吗 | **不会**——`*_gen.go`/`*_generated.java`/纯数据 DTO/配置类等一律排除；工具函数/私有方法不作为功能入口；见执行边界清单 `references/execution-boundaries.md` |
| 单个函数条件特别多 | 按执行顺序编号保证可追溯；覆盖说明会给出判定点→用例矩阵 |
| 只测某个模块 | 直接指定子目录或文件路径即可 |
