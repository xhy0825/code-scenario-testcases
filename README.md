# code-scenario-testcases

**代码逻辑驱动的研发自测用例生成器** —— 读取业务代码，自动梳理业务场景与功能，把代码中所有 `if/else/switch` 条件分支转成研发自测用例，输出带覆盖核算的 Excel 表格。

- **语言无关**：支持 Java / Go / Python / JavaScript / TypeScript / C# / C / C++ / Rust 等主流语言
- **可核算的覆盖率**：入口覆盖、判定点覆盖以真实代码盘点为分母，缺漏会亮红灯而非悄悄漏
- **支持变更范围扫描**：`-all` 全量、`-diff` 当前未提交变更、`-diff [commitId]` 指定提交之后变更

## 一、功能介绍

### 1.1 核心能力

| 能力 | 说明 |
|---|---|
| **三级结构** | 业务场景 → 功能 → 条件分支用例，从用户视角到代码判定逐层对应 |
| **分支全覆盖** | 把 `if/else`、`switch/case`、三目、guard clause、循环内条件统一建模为"判定点"，每个分支一条用例 |
| **预期结果** | 不通过/校验失败分支写出功能"展示的结果"（错误码+文案、提示、跳转、异常）；代码里直接 `throw`/`return` 的错误串**原样摘录** |
| **覆盖率核算** | 判定点盘点清单 + 第二遍回读源码双向核对，产出覆盖统计与判定点→用例追溯矩阵 |
| **变更回归覆盖** | `-diff` 模式下定位受影响函数，以**整函数**为单位生成完整分支用例（防一次改动回归到其它分支） |
| **命令式范围控制** | 用 `code-scenario-testcases -all / -diff / -diff [commitId]` 指令精确控制扫描范围 |
| **测试结果跟踪** | 用例表内置 **测试结果列（PASS/FAIL 下拉）**，研发自测执行时直接勾选 |
| **语言无关建模** | 条件逻辑统一建模，语言差异只影响入口识别与语法写法（详见 `references/language-guide.md`） |

### 1.2 产出物

一次调用产出两个文件：

1. **研发自测用例 Excel**（`.xlsx`）—— 主 sheet + 「覆盖说明」sheet
2. **结构化用例 JSON**（`cases.json`）—— 供二次消费/接入测试平台

#### 主 sheet 列说明

| 列 | 说明 |
|---|---|
| 用例编号 | `TC-<场景缩写>-<序号>` |
| 业务场景 | 用户视角动作（如"订单管理"） |
| 功能 | 一个可独立触发的业务入口 |
| 用例名称 | "功能名 + 分支语义" |
| 前置条件 | 触发该分支所需的数据/状态前提 |
| 操作步骤 | 可复现步骤（调用入口 + 关键参数 + 数据准备） |
| 优先级 | P0 核心/安全校验；P1 主要分支；P2 边缘/兜底 |
| 预期结果 | **核心字段**，不通过分支写功能展示的结果 |
| 测试结果 | 留空，下拉选择 PASS / FAIL（数据验证） |
| 备注 | 外部依赖、待验证事项、边界提示 |
| 代码位置 | 分支所在 `文件:行号` |

#### 「覆盖说明」sheet

- **覆盖统计**：业务入口覆盖 X/Y、判定点覆盖 X/Y
- **变更范围**（`-diff` 模式）：变更文件数、受影响函数、新增判定点
- **缺口列表**：未达 100% 时列出具体缺口
- **判定点 → 用例追溯矩阵**：每个判定点的每个分支映射到用例编号
- **无法静态验证项**：外部依赖行为、需求未实现场景等，显式标注、不混入统计

### 1.3 三级结构

```
业务场景（用户视角：如"订单管理"）
└── 功能（业务入口：查询订单 / 创建订单 / 取消订单）
    └── 条件分支用例（每个 if/else/switch 分支一条用例）
```

## 二、架构设计

### 2.1 目录结构

```
code-scenario-testcases/
├── SKILL.md                        # 技能主体：工作流程 + 字段规则 + 调用方式
├── references/
│   └── language-guide.md           # 语言适配参考（按需加载）
│       ├── 文件扩展名 → 语言映射
│       ├── 各语言"功能入口"识别启发式
│       ├── 条件分支语法对照表
│       └── 判定点统一建模规则
├── scripts/
│   └── generate_excel.py           # 结构化 JSON → Excel 生成脚本
│       ├── 主 sheet（11 列 + 样式 + 筛选 + 冻结首行）
│       ├── 测试结果列 PASS/FAIL 下拉（数据验证）
│       └── 「覆盖说明」sheet（统计/矩阵/缺口/变更范围/标注）
└── evals/
    └── evals.json                  # 测试用例定义（5 个 eval，用于回归验证）
```

### 2.2 数据流

```
扫描目录 / git diff
   │
   ▼
① 扫描过滤源码 ──▶ ② 识别业务场景/功能（产出入口清单）
   │
   ▼
③ 逐功能提取判定点，生成分支用例
   │
   ▼
④ 覆盖率核对（判定点盘点 + 双向回读 + 覆盖统计）
   │
   ▼
⑤ 整理成 cases.json（cases + coverage 对象）
   │
   ▼
⑥ scripts/generate_excel.py ──▶ 研发自测用例.xlsx + cases.json
```

### 2.3 cases.json 数据结构

```jsonc
{
  "cases": [
    {
      "case_id": "TC-ORD-001",
      "scenario": "订单管理",
      "function": "创建订单",
      "name": "创建订单-用户为空校验",
      "precondition": "调用创建订单接口",
      "steps": ["body 传 {userId:null}"],
      "priority": "P0",
      "expected_result": "返回错误\"用户不能为空\"",
      "test_result": "",           // 留空，Excel 中下拉选择
      "remark": "",                // 补充说明
      "code_location": "OrderService.java:3"
    }
  ],
  "coverage": {
    "stats": { "entry_covered": 1, "entry_total": 1, "dp_covered": 5, "dp_total": 5 },
    "inventory": [                 // 判定点→用例追溯矩阵
      { "function": "创建订单", "decision_point": "if (...)",
        "line": "OrderService.java:3", "branches": ["真→TC-ORD-001", "假→TC-ORD-002"] }
    ],
    "change_scope": {              // -diff 模式才产生
      "mode": "diff",
      "changed_files": ["OrderService.java"],
      "affected_functions": ["createOrder"],
      "new_decision_points": ["if (amount > 10000)"]
    },
    "uncovered": [],               // 缺口，为空表示全覆盖
    "notes": ["orderDao 为外部依赖，行为无法静态验证"]
  }
}
```

### 2.4 关键设计决策

| 决策 | 理由 |
|---|---|
| **判定点统一建模** | `if/else/switch/三目/guard/循环内条件` 都抽象为"判定点 → 真/假分支"，跨语言一致 |
| **嵌套条件不笛卡尔积** | 内层分支把外层取值写进**前置条件**，每个判定点自身覆盖真假分支，避免用例爆炸 |
| **受影响函数整函数覆盖**（-diff） | 一次改动可能回归到该函数其它分支，整函数覆盖比"只改哪测哪"安全 |
| **覆盖率以"代码可表达范围"为分母** | 外部依赖行为、需求未实现场景无法由静态代码保证 → 显式标注而非假装覆盖 |
| **第二遍回读双向核对** | 有判定点无用例 → 补；有用例无代码依据 → 删/标；让"漏没漏"可核算、可追责 |

### 2.5 工作流程（6 步）

1. **扫描与过滤**：递归收集源码，跳过构建产物/依赖/测试文件
2. **识别业务场景与功能**：按 Controller/业务实体/模块聚合场景，产出功能入口清单
3. **逐功能提取分支并生成用例**：识别全部判定点，每分支一条用例
4. **覆盖率核对**：判定点盘点清单 + 第二遍回读双向核对 + 覆盖统计
5. **生成 Excel**：`cases.json` → `generate_excel.py` → xlsx（含覆盖说明 sheet）
6. **汇报**：场景/功能/用例数 + 覆盖率（入口 X/Y、判定点 X/Y）+ 文件路径

## 三、使用帮助

### 3.1 环境要求

- Claude Code（本 skill 运行环境）
- Python 3 + `openpyxl`（生成 Excel 用，缺失时先执行 `pip install openpyxl`）
- `-diff` 模式需要 git 仓库

### 3.2 调用方式

| 指令 | 含义 | 扫描范围 |
|---|---|---|
| `code-scenario-testcases -all` | 全量扫描 | 整个目录的业务代码（默认行为） |
| `code-scenario-testcases -diff` | 当前变更 | 仅未提交变更（工作区+暂存区+未跟踪新文件）涉及的代码 |
| `code-scenario-testcases -diff [commitId]` | 指定提交之后 | 从 `[commitId]` 到当前（含未提交）的变更代码 |

也支持自然语言触发，例如：

- "根据 D:/project/order 目录下的代码生成研发自测用例"
- "把 createOrder 接口的 if/else/switch 分支整理成测试用例"
- "我刚改了注册逻辑还没提交，用 -diff 生成本次变更的自测用例"

### 3.3 输入方式

- **目录**（推荐）：递归扫描其中源码文件
- **单个文件 / 单个函数**：只分析指定对象
- **粘贴的代码片段**：直接贴进对话

未指定范围时默认全目录扫描，并在汇报中说明覆盖范围。

### 3.4 使用示例

**示例 1：全量扫描**

```
code-scenario-testcases -all
```

扫描当前项目全部业务代码 → 生成 `研发自测用例_YYYYMMDD.xlsx` + `cases.json`。

**示例 2：当前未提交变更**

```
code-scenario-testcases -diff
```

用 `git diff HEAD` 定位变更文件 → 定位受影响函数 → 对受影响函数生成完整分支用例，备注标注"本次变更影响"，覆盖说明单列变更范围。

**示例 3：指定提交之后的变更**

```
code-scenario-testcases -diff a1b2c3d
```

`git diff a1b2c3d` 得到该提交之后到当前的全部变更（含已提交 + 未提交），适合"上一个发布节点之后我改了什么，就测什么"。

### 3.5 输出解读

打开生成的 Excel：

1. **主 sheet**：按行一条用例。建议按「优先级」筛选，先执行 P0（核心流程/权限安全校验）
2. **测试结果列**：执行时点开下拉选 PASS / FAIL；未执行留空
3. **覆盖说明 sheet**：
   - 看「判定点覆盖」是否为 X/X —— 不到 100% 时「缺口」会列出漏了什么
   - 追溯矩阵帮你定位"某条用例测的是代码哪一行哪个条件"
   - 「无法静态验证项」是需要你在自测环境额外验证的（如外部依赖）

### 3.6 覆盖率口径与边界

- 覆盖率以**代码可表达的范围**为分母（入口清单、判定点盘点），不包含：
  - 需求存在但代码未实现的场景
  - 外部系统行为（DB / 缓存 / 第三方接口）
  - 框架级隐含行为（参数反序列化、鉴权拦截）
- 这些项会**显式标注**在「无法静态验证项」中，而不是假装覆盖
- 代码本身写死/未实现的行为，按代码现状如实写出并在备注标注

### 3.7 常见问题

| 问题 | 处理 |
|---|---|
| 目录不是 git 仓库 | `-diff` 自动回退为全量扫描，并在汇报中说明原因 |
| `-diff` 但没有变更 | 变更集为空时回退全量扫描，汇报说明 |
| 环境缺 openpyxl | 先 `pip install openpyxl`，脚本会提示 |
| 外部依赖无法静态验证 | 预期结果按代码现状书写，在「无法静态验证项」标注，需自测环境验证 |
| 单个函数条件特别多 | 按执行顺序编号保证可追溯；覆盖说明会给出判定点→用例矩阵 |
| 只测某个模块 | 直接指定子目录或文件路径即可 |
