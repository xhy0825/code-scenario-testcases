> **版本**：v1.20（本设计对应版本）
> **状态**：待实施

## 背景与目标

当前 skill 生成的用例 Excel 中：

- **前置条件**列只要求"可构造的数据/状态前提"，未区分该前置是通过**页面 UI 操作到达**还是通过 **mock 数据/接口调用**构造——执行者看到"登录态有效，库存充足"不知道要不要先搭页面环境还是先 mock 服务。
- **预期结果**列只要求"可判定且单一"，未区分**页面/客户端显示的现象**（UI 层可观察物）与**接口/数据/状态的落库结果**（数据层可观察物）——研发自测时难以区分"界面对了但数据错了"与"数据对了但界面没展示"。

目标：**列结构不变（保持 15 列），强化两列的填写规范**——

1. **前置条件**：每条用例前置以 `[页面触发]` 或 `[mock数据]` 开头，明确触发方式（页面 UI 操作 vs 数据/接口构造）。
2. **预期结果**：每条用例预期统一为 `UI显示: <页面/客户端现象>;数据结果: <接口/数据/状态变化>`，强制分离 UI 显示现象结果与数据结果。

## 设计方案

### 1. 前置条件列强制标注触发方式

- **格式**：`[页面触发] <页面状态前提>` 或 `[mock数据] <数据/状态前提>`
- **触发方式二值定义**：

| 触发方式 | 判定特征（按操作步骤的入口方式） | 典型前置写法 |
|---|---|---|
| `[页面触发]` | 步骤是页面操作（点击/输入/进入页面/导航） | `[页面触发] 已登录，进入商品详情页` |
| `[mock数据]` | 步骤是接口调用 / 依赖 mock / 数据预置 | `[mock数据] mock 库存服务返回 false`<br>`[mock数据] 订单表预置 status=PAID 的订单` |

- **判定规则**：看该用例**操作步骤的入口方式**——步骤以页面操作为主 → `[页面触发]`；步骤以调用接口/mock 依赖/预置数据为主 → `[mock数据]`。两者皆有可能时（如"页面点击后触发接口"），按**前置构造是否依赖页面环境**判定：前置需要在真实页面环境到达 → `[页面触发]`；前置只靠数据即可构造 → `[mock数据]`。
- **与既有列的联动**：`[页面触发]` 的用例验证方法偏 `界面操作`、可自动化程度偏 `可端到端`；`[mock数据]` 的用例验证方法偏 `接口响应`/`数据状态`、可自动化程度偏 `可单测`/`可组件测试`。
- **来源说明保留**：前置条件来源（代码摘录 / 推断）仍写备注，不在前缀里。

### 2. 预期结果列强制分离 UI 显示现象与数据结果

- **格式**：`UI显示: <页面/客户端现象>;数据结果: <接口/数据/状态变化>`
- **三种写法**（强制双部分，无则显式标注）：

| 情形 | 写法 |
|---|---|
| 两者都有 | `UI显示: 页面提示"库存不足";数据结果: 订单未生成(查库)` |
| 纯接口（无 UI 层） | `UI显示: 无(纯接口);数据结果: HTTP 200 + data 含商品` |
| 纯展示（无数据变化） | `UI显示: 显示"VIP";数据结果: 无(纯展示)` |

- **既有规则全部保留**：
  - 预期结果必须**可判定且单一**（精确到返回体/状态码/文案/异常/判定标准），不可判定的"返回商品数据"类不合格
  - 错误串**原样摘录**
  - 来源标注（代码摘录 / 推断需联调）写备注
  - **可观察对象 = 研发实际看到的**，且必须与「验证方法」列匹配（验证方法说"看日志"，预期必须给出日志里的判定点；验证方法说"界面操作"，`UI显示:` 必须给出页面现象）

### 3. 字段质量自检 10 → 12 条

新增 2 条（追加在既有 10 条之后）：

```
11. **前置条件触发方式标注正确**——前缀 `[页面触发]`/`[mock数据]` 与操作步骤入口方式一致（页面操作→页面触发；接口调用/mock/数据预置→mock数据），不混用不臆测
12. **预期结果双结果完整**——含 `UI显示:` 与 `数据结果:` 两部分；纯接口写 `UI显示: 无(纯接口)`、纯展示写 `数据结果: 无(纯展示)`，不省略任何一部分
```
